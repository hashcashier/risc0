## Diagnostic 11: surface silent GPU fallback under `gpu_authoritative=true` (2026-05-12)

**Refined hypothesis (post-D10)**: `finish_hal_op` at `risc0/zkp/src/hal/webgpu.rs:5074` contains a silent-corruption path. When `gpu_authoritative=true` and the dispatch returns `Ok(false)` (silent fallback — e.g., a `raw_buffer()` is `None`, a precondition fails, or `can_dispatch_*` is more permissive than the actual dispatch), the `else` branch unconditionally runs `cpu_mirror()`. But the per-op `_async` wrappers (`batch_expand_into_evaluate_ntt_async`, `batch_bit_reverse_async`, `hash_rows_async`, …) only sync inputs to CPU when `!gpu_authoritative` — so under this fallback, `cpu_mirror` computes on stale CPU shadows. `mark_cpu_result(false)` then marks the output `cpu_dirty=true, cpu_stale=false` (CPU current), which the next op reads as authoritative truth. The downstream Merkle hash sees zero-shadow data and produces an all-zero root, matching the observed three-group zero-root signature at segments 5/8.

This explains the symptom shape:
1. Multi-segment proofs hit `can_dispatch_*` vs dispatch mismatch only after enough HAL state has accumulated (matches "failure only after several lifts succeed").
2. All three commit groups (CTRL, DATA, ACCUM) fail simultaneously at one segment (the shared upstream NTT/expand op produces stale data; every downstream group hashes zeros).
3. Computation timings appear normal in some runs (the CPU mirror runs to completion — it's just operating on wrong data).
4. Failure is non-deterministic across runs (segment 5 vs 8) because which dispatch returns `Ok(false)` depends on GPU scheduling and prior cumulative state.

**Diagnostic**: Add a wasm32-only panic in the `gpu_authoritative=true && !gpu_used` branch of `finish_hal_op` that includes the op `name`. If D11 fires before xgboost's lift completes, the panic message reveals which op is silently falling back — that's the call site to fix.

Code change (kept in worktree until SP-CR closes):

```rust
#[cfg(all(feature = "webgpu", target_arch = "wasm32", target_os = "unknown"))]
if self.gpu_authoritative() && !gpu_used {
    panic!(
        "verify_failed_at: silent_gpu_fallback name='{}' under gpu_authoritative=true (inputs may be stale)",
        name
    );
}
```

Compile-check (`cargo check --target wasm32-unknown-unknown -p risc0-zkp --features webgpu`) passes.

**Audit of dispatch_*** (post-D11)**: walked `risc0/zkp/src/hal/webgpu.rs` to compare each `can_dispatch_*` with its `dispatch_*` for precondition gaps. Confirmed mismatch in the Poseidon2 path: `dispatch_poseidon2_hash_rows` at line 9397 and `dispatch_poseidon2_hash_fold` at line 9339 both require `hash.round_constants.raw_buffer().is_some()` and `hash.m_int_diag.raw_buffer().is_some()`, but neither `can_dispatch_hash_rows` (line 6349) nor `can_dispatch_hash_fold` (line 6341) checked those. This is the smoking gun: when either constant buffer's `raw_buffer` is `None` (e.g., not yet materialized for that lift, or transiently dropped), `can_dispatch=true` but `dispatch=Ok(false)` silently → `finish_hal_op`'s `cpu_mirror` runs on stale CPU shadows (the `_async` wrapper skipped the input sync because `gpu_authoritative=true && can_dispatch=true`) → Poseidon2 cpu_mirror hashes the zero-initialized CPU shadow → all three commit groups at the failing segment commit zero Merkle roots → control_id check in `verify_integrity` reports `f765ab6e0c…` (the SHA of zero-roots), which is not a known program → fast-fail with 1 ms `verify_lift`. Matches every observed symptom (non-determinism = whether the constants happen to be materialized at the relevant call site that day).

## Fix (SP-CR landing)

Tightened both `can_dispatch_hash_rows` and `can_dispatch_hash_fold` to mirror the dispatcher's full precondition set, including the Poseidon2 round-constants and `m_int_diag` raw-buffer presence checks. With this, when either constant buffer's GPU side isn't ready, `can_dispatch` correctly returns `false`, the `_async` wrapper takes the `!gpu_authoritative || !can_dispatch` branch and syncs the matrix/io input to CPU before dispatch. Then either:
- the sync re-materializes the GPU side via `sync_cpu_to_gpu` during dispatch — and dispatch succeeds on GPU; or
- dispatch still returns `Ok(false)`, but `cpu_mirror` now has CPU-current inputs and produces correct hash output.

Either way, the silent zero-root corruption is eliminated. D11 stays in place as a tripwire — any *other* `can_dispatch_*` / `dispatch_*` gap will now panic with the op name at the cpu_mirror site instead of corrupting downstream Merkle roots.

## Diagnostic 14 result (2026-05-12 — root cause IDENTIFIED)

**Outcome**: D14 (`onuncapturederror` listener at `request_device()`) fired with the actual Chrome WebGPU error during xgboost. The first uncaptured error, fired during segment 8's `recursion_witgen`:

```
browser-prove:webgpu-uncaptured-error type=GPUOutOfMemoryError
  msg=vkAllocateMemory failed with VK_ERROR_OUT_OF_DEVICE_MEMORY
  at CheckVkOOMThenSuccessImpl (third_party/dawn/src/dawn/native/vulkan/VulkanError.cpp:119)
```

Followed by 1235 cascading `GPUValidationError`s on the buffer that failed to allocate — most often `[Invalid Buffer "data"]` (recursion's `witgen.data`, ~208 MiB at lift_18 po2). The cascade includes failed `queue.writeBuffer` calls into 16 MiB chunks of `data`, failed bind_group creations that reference `data`, and ultimately failed `[Queue].Submit([Invalid CommandBuffer])` for downstream dispatches that touch `data`.

**Cumulative VRAM pressure**: each xgboost segment lift allocates ~1-2 GiB of transient GPU buffers (data, accum, coeffs, evaluated, nodes for three groups). Without explicit `.destroy()`, JS GC of `GpuBuffer` handles is the only release mechanism, and it does not run promptly enough between hot-loop dispatches. After 7-8 segments (~8-16 GiB cumulative VRAM held), Chrome Dawn's per-context memory budget is exhausted; the next `device.createBuffer` for `witgen.data` returns a handle that's internally marked invalid but synchronously appears "ok". Subsequent writes/reads silently fail, producing all-zero Merkle roots — exactly the regression's symptom.

This **falsifies** the working theory that the bug is in the `gpu_authoritative=true` cpu_mirror fallback path (D11) or in any dispatch-precondition mismatch (D11.5 / can_dispatch_hash_*). The bug is a **pure resource leak**: the WebGPU prover never explicitly destroys its GPU buffers and depends on JS GC, which is too slow for the recursion lift's allocation pattern.

## Diagnostic 16 fix (2026-05-12 — explicit GpuBuffer destruction)

Wrap `web_sys::GpuBuffer` in a new `WebGpuBufferOwner` struct whose `Drop` calls `buffer.destroy()`. Change `WebGpuBuffer.gpu` from `Option<web_sys::GpuBuffer>` to `Option<Rc<WebGpuBufferOwner>>`. The existing `Clone` derive on `WebGpuBuffer` clones the `Rc`, sharing the owner across slice/clone operations. When the *last* `Rc` clone drops (at end of lift scope), `WebGpuBufferOwner::drop` runs and explicitly releases the GPU memory via `GPUBuffer.destroy()`.

This is surgical: ~30 lines changed in `risc0/zkp/src/hal/webgpu.rs` (new struct + Drop, type change on one field, one alloc call site updated, `raw_buffer()` accessor updated). No change to dispatch / kernel code. Multi-lift VRAM growth is bounded by the active lift's working set instead of the cumulative-across-all-lifts ceiling that triggered the OOM.

D14 (`onuncapturederror` listener) is kept in production — it costs nothing in the happy path and surfaces any *future* silent GPU errors immediately.
