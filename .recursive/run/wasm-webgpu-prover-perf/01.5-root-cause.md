## Data Flow Trace

Segment 8's lift sequence inside `composite_to_succinct_async`:

1. Loop iter 8 enters with `continuation_receipt = Some(joined_0..7)` (the join of segments 0-7).
2. `let lifted = self.lift_async(right=segments[8]).await?` is called.
3. `lift_async` enters; timer starts.
4. `lift_webgpu(segments[8], hal).await?` runs:
   - `recursion_witgen` runs (169 ms — normal)
   - `recursion_accumulate` runs (215 ms — normal)
   - `eval_check_base_private_interpreter_submit` (0 ms; dispatch enqueued)
   - `finalize_async`'s stages run with ANOMALOUSLY SHORT times for `check_group`, `eval_u_groups`, `eval_u_check`, `fri_prove`.
5. `lift_webgpu` returns Ok with a malformed `SuccinctReceipt<ReceiptClaim>`.
6. `verify_lift` runs `receipt.verify_integrity()` → returns Err → annotated `"verify lift"` → propagates up.

Between iter 7 and iter 8 of the loop, the IMMEDIATELY prior work was `join_async` (joining lifted_7 with the continuation `joined_0..6`). That join_async also ran a finalize_async pipeline with the SAME stage names (check_group, eval_u_groups, fri_prove, etc.). The seg8 lift may be inheriting some HAL state from that join.

Candidate state pollution sources:
- `eval_check_interpreter_pipelines: RefCell<BTreeMap>` at `risc0/zkp/src/hal/webgpu.rs:854`–855 (cached compiled pipelines).
- The recursion data group (`group2`) which is chunk-uploaded per-proof and may persist between consecutive recursion proofs.
- Async/dirty-bit-tracked `WebGpuBuffer` mirrors. If a buffer was marked GPU-owned by a join's finalize and then read incorrectly by a lift's finalize (or vice versa), the result would be garbage data passed through to FRI/DEEP.

## Pattern Analysis

The seg8 lift is the only abnormal one in xgboost's 11-segment run (segments 0-7 lifts and joins all show normal stage timings). The boundary that breaks is **lift IMMEDIATELY following the cumulative join** — i.e., when the recursion HAL state has been heavily used by a join immediately prior. This is a unique signature.

For poseidon2_basic / libm / hello-world / json / cfg / keccak_union_small (R1 smoke), there is at most ONE segment and therefore NO `join_async` calls (`continuation_receipt` is None on iter 0, so the else branch runs and no join happens). For `keccak_union_small` with 4 segments, the lift-after-join pattern DOES happen — but it works. So why does xgboost's 11-segment lift-after-join break at segment 8 specifically?

Possible refinement of the hypothesis: A counter, cache index, or pipeline-cache eviction threshold tied to N (the iteration count) trips at iter 8 specifically. For example:
- An LRU cache with capacity 8 evicts an entry at iter 8.
- A buffer pool counter overflows or wraps at iter 8.
- A counter modulo some value triggers a different code path at iter 8.

The `eval_check_interpreter_pipelines` map at `risc0/zkp/src/hal/webgpu.rs:854`–855 has no LRU per Phase 1 inventory. But other caches in the system may.

## Hypothesis Testing (focused, to confirm under SP-CR)

**Working hypothesis** (highest-likelihood, lowest-cost to test):

> Between joins and the immediately-following lift, a WebGPU buffer that should be re-initialized per-call retains stale (or zero-filled) data from the join, causing the lift's finalize_async stages (check_group, eval_u_groups, fri_prove) to operate on empty/wrong data and return a structurally-valid but FRI-incorrect receipt. The trigger at iter 8 (rather than earlier) is likely tied to a numeric threshold or cumulative state count, not iter index itself.

**Confirmation strategy** (SP-CR's "Form a root-cause hypothesis. Confirm via instrumentation" checklist item):

1. **Add `WebGpuStageTimer` scopes** inside `risc0/circuit/recursion/src/prove/hal/webgpu.rs` around `recursion_finalize` (and its sub-stages if not already scoped) to capture buffer state at start of each lift's finalize. Log byte hashes of the input buffers to compare across lifts.
2. **Re-run xgboost** and check whether seg8's input buffers to fri_prove/eval_u_groups differ from seg7's lift's inputs — if seg8's inputs hash to zero or to a partial seg7-join residue, the buffer-staleness hypothesis is confirmed.
3. **Alternative quick test**: try `multi_test/keccak_union` (KeccakUnion(3), 11 segments) which also exercises lift-after-join at high segment count. If it ALSO fails at lift, the bug is multi-segment-general; if it passes, xgboost is special.
4. **Pipeline-cache audit**: instrument `eval_check_interpreter_pipeline()` at `risc0/zkp/src/hal/webgpu.rs:4996` to log cache hits/misses per stage call. A miss → hit transition at iter 8 would correlate with the regression.

## Root Cause Summary (provisional, pending confirmation)

The xgboost `verify lift` failure on segment 8 is a **multi-segment correctness regression at the lift-after-join boundary** in the async/GPU-authoritative recursion path. The specific failure mode is anomalously short `finalize_async` sub-stages (`check_group`, `eval_u_groups`, `eval_u_check`, `fri_prove`) for segment 8's lift, producing a structurally-valid but FRI-incorrect `SuccinctReceipt<ReceiptClaim>` that fails integrity verification.

The trigger at iter 8 (rather than earlier) is likely tied to a state-count or cache-eviction threshold, not the iteration index. The bug is almost certainly in the WebGPU HAL or the recursion circuit HAL's async path, introduced by one of the pre-Phase-0 "speeds" / "less cpu more gpu" commits.
