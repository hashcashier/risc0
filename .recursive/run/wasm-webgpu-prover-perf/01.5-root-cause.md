## Reproduction Verification

Two Chrome runs captured (2026-05-12). Both fail with `verify lift`, but the failure point differs between runs — **the bug is non-deterministic**:

| Run | Failing segment | Lift wall time (failing seg) | verify_lift (failing seg) | Total prove_session_async |
| --- | ---: | ---: | ---: | ---: |
| 1 (`evidence/perf/r9-deferred/xgboost.chrome.txt`) | **segment 8** | 642 ms (anomalously short; finalize stages 100×+ faster than peers) | 1 ms | 103.585 s |
| 2 (`evidence/logs/sp-cr-xgboost-repro-*.txt`) | **segment 5** | 2555 ms (NORMAL; finalize stages all 670/900 ms, indistinguishable from passing peers) | 1 ms | 89.02 s |

This is a **major** finding that changes the hypothesis. Run 2's failing segment 5 had completely normal finalize_async stage timings — eval_u_groups 670 ms, fri_prove 900 ms, no anomaly. Yet verify_lift still returned Err in 1 ms. Both runs share the 1 ms verify_lift signature, suggesting the receipt's integrity check short-circuits early on a structural mismatch (e.g., wrong claim hash, wrong control root).

The non-determinism rules out a simple deterministic logic bug. Most likely candidates:
- **Race condition in async dispatches**: a downstream stage reads a buffer before the upstream GPU write completes; some fence/sync is missing.
- **Non-deterministic GPU side effect**: e.g., uninitialized memory in an alloc that downstream reads.
- **Pipeline/buffer reuse with weak invalidation**: WGSL pipeline or `WebGpuBuffer` state carries cross-call state that depends on timing.

The failure is reliably triggered (2 of 2 runs failed), but the failing segment index varies (5 vs 8). This narrows the bug to the **lift-after-join boundary** but is NOT correlated with any specific stage timing pattern.

## Data Flow Trace

Segment 8's lift sequence inside `composite_to_succinct_async`:

1. Loop iter 8 enters with `continuation_receipt = Some(joined_0..7)` (the join of segments 0-7).
2. `let lifted = self.lift_async(right=segments[8]).await?` is called.
3. `lift_async` enters; timer starts.
4. `lift_webgpu(segments[8], hal).await?` runs:
   - `recursion_witgen` runs (169 ms — normal)
   - `recursion_accumulate` runs (215 ms — normal)
   - `eval_check_base_private_interpreter_submit` (0 ms; dispatch enqueued)
   - `finalize_async`'s stages run with ANOMALOUSLY SHORT times for `check_group`, `eval_u_groups`, `eval_u_check`, `fri_prove`.
5. `lift_webgpu` returns Ok with a malformed `SuccinctReceipt<ReceiptClaim>`.
6. `verify_lift` runs `receipt.verify_integrity()` → returns Err → annotated `"verify lift"` → propagates up.

Between iter 7 and iter 8 of the loop, the IMMEDIATELY prior work was `join_async` (joining lifted_7 with the continuation `joined_0..6`). That join_async also ran a finalize_async pipeline with the SAME stage names (check_group, eval_u_groups, fri_prove, etc.). The seg8 lift may be inheriting some HAL state from that join.

Candidate state pollution sources:
- `eval_check_interpreter_pipelines: RefCell<BTreeMap>` at `risc0/zkp/src/hal/webgpu.rs:854`–855 (cached compiled pipelines).
- The recursion data group (`group2`) which is chunk-uploaded per-proof and may persist between consecutive recursion proofs.
- Async/dirty-bit-tracked `WebGpuBuffer` mirrors. If a buffer was marked GPU-owned by a join's finalize and then read incorrectly by a lift's finalize (or vice versa), the result would be garbage data passed through to FRI/DEEP.

## Pattern Analysis

The seg8 lift is the only abnormal one in xgboost's 11-segment run (segments 0-7 lifts and joins all show normal stage timings). The boundary that breaks is **lift IMMEDIATELY following the cumulative join** — i.e., when the recursion HAL state has been heavily used by a join immediately prior. This is a unique signature.

For poseidon2_basic / libm / hello-world / json / cfg / keccak_union_small (R1 smoke), there is at most ONE segment and therefore NO `join_async` calls (`continuation_receipt` is None on iter 0, so the else branch runs and no join happens). For `keccak_union_small` with 4 segments, the lift-after-join pattern DOES happen — but it works. So why does xgboost's 11-segment lift-after-join break at segment 8 specifically?

Possible refinement of the hypothesis: A counter, cache index, or pipeline-cache eviction threshold tied to N (the iteration count) trips at iter 8 specifically. For example:
- An LRU cache with capacity 8 evicts an entry at iter 8.
- A buffer pool counter overflows or wraps at iter 8.
- A counter modulo some value triggers a different code path at iter 8.

The `eval_check_interpreter_pipelines` map at `risc0/zkp/src/hal/webgpu.rs:854`–855 has no LRU per Phase 1 inventory. But other caches in the system may.

## Hypothesis Testing (revised after run 2)

**Revised working hypothesis** (updated 2026-05-12 after run 2 showed non-deterministic failure point):

> The xgboost `verify lift` failure is a **race condition or missing async fence** in the multi-segment lift/join async path. Two reproductions failed at different segments (seg5 and seg8), but both with a 1 ms `verify_lift` signature consistent with a structural receipt mismatch detected on the first integrity check. The non-determinism rules out a deterministic logic bug; it points at:
> 1. Missing `queue.submit()` or `await sync_gpu_to_cpu()` somewhere in the lift_webgpu → finalize_async pipeline that lets a downstream stage read a buffer before the upstream GPU write completes.
> 2. A buffer that's read by the verifier (control_root, claim hash, or transcript) without proper read-fence after the GPU write.
> 3. A timing-dependent reuse of a `WebGpuBuffer` whose dirty-bit invalidation is racy under contended GPU scheduling.

**Why the earlier hypothesis ("buffer staleness producing skipped work") was wrong**: run 2's failing seg5 lift had completely normal stage timings (eval_u_groups 670ms, fri_prove 900ms). If the bug were "skipped work due to stale buffer", run 2 would have shown anomalous fast timings like run 1. The fact that run 2 had normal timings but still failed verify_lift means the work WAS done, but its OUTPUT was inconsistent with its claim — consistent with a race condition reading stale state, not a buffer-skip.

**Confirmation strategy** (SP-CR's "Form a root-cause hypothesis. Confirm via instrumentation" checklist item):

1. **Add `WebGpuStageTimer` scopes** inside `risc0/circuit/recursion/src/prove/hal/webgpu.rs` around `recursion_finalize` (and its sub-stages if not already scoped) to capture buffer state at start of each lift's finalize. Log byte hashes of the input buffers to compare across lifts.
2. **Re-run xgboost** and check whether seg8's input buffers to fri_prove/eval_u_groups differ from seg7's lift's inputs — if seg8's inputs hash to zero or to a partial seg7-join residue, the buffer-staleness hypothesis is confirmed.
3. **Alternative quick test**: try `multi_test/keccak_union` (KeccakUnion(3), 11 segments) which also exercises lift-after-join at high segment count. If it ALSO fails at lift, the bug is multi-segment-general; if it passes, xgboost is special.
4. **Pipeline-cache audit**: instrument `eval_check_interpreter_pipeline()` at `risc0/zkp/src/hal/webgpu.rs:4996` to log cache hits/misses per stage call. A miss → hit transition at iter 8 would correlate with the regression.

## Root Cause Summary (provisional, after run 2)

The xgboost `verify lift` failure is a **non-deterministic correctness regression at the multi-segment lift/join async boundary** in the WebGPU recursion path. Two reproductions show the bug:
- Run 1: failure at segment 8, lift wall time 642ms (anomalously short)
- Run 2: failure at segment 5, lift wall time 2555ms (normal)

Both failures share: 1 ms `verify_lift` indicating an integrity check short-circuited early, consistent with a structural receipt mismatch (wrong control root, wrong claim hash, or wrong transcript).

**Bug class**: race condition or missing async sync in the multi-segment lift/join path. NOT a buffer-staleness-skips-work bug (run 2 disproves that).

**Bug locus**: somewhere in the `lift_webgpu` → `finalize_async` pipeline (in `risc0/zkp/src/prove/prover.rs:487`–and-following) or in the recursion circuit HAL's async eval_check/witness path. The introduction is most likely in the pre-Phase-0 "speeds" / "less cpu more gpu" series of commits that wired the async/GPU-authoritative recursion path.

## Diagnostic 2: `wait_idle()` at end of recursion `prove_async` (2026-05-12)

To test the "queued GPU work not completed before consumer" hypothesis, an `await self.hal.wait_idle()` barrier was inserted at the end of `risc0/circuit/recursion/src/prove/hal/webgpu.rs:prove_async`, immediately before returning the `RecursionReceipt`. This forces all queued WebGPU work to complete before the receipt is constructed.

Re-run xgboost (evidence at `.recursive/run/wasm-webgpu-prover-perf/evidence/logs/sp-cr-xgboost-waitidle-*.txt`):
- Segments 0–7 lift cleanly with normal stage timings (2575–2700ms each, verify_lift 13–17ms).
- **Segment 8 fails with `verify lift` after lift_async elapsed_ms=1260** (vs original run 1's 642ms and run 2's 2555ms).
- Stage timings for segment 8's lift no longer have the dramatic anomalies of run 1 (eval_u_groups, fri_prove are closer to normal).
- Total wall time: 104.48 s.

**Conclusion**: The end-of-prove_async `wait_idle()` barrier partially helped (segment 8's lift went from 642ms → 1260ms, but still abnormally fast for a normal recursion lift). It did NOT prevent verify_lift failure. **The corruption happens DURING prove_async, not at the prove→verify boundary.** The receipt's seal is already incorrect when prove_async returns; wait_idle at the end can't reconstitute the bad data.

This further narrows the bug locus: the corruption is upstream of the seal's final assembly, somewhere in the multi-stage finalize_async pipeline (check_group, eval_u_groups, fri_prove). The race is in how those stages read each other's outputs or shared HAL state across consecutive lifts.

The wait_idle change has been REVERTED.

## Diagnostic 1: gpu_authoritative_scope toggled to false (2026-05-12)

To test the race-condition hypothesis, the recursion async path's `gpu_authoritative_scope(true)` was temporarily replaced with `gpu_authoritative_scope(false)` in `risc0/circuit/recursion/src/prove/hal/webgpu.rs` (the two scoped blocks around `commit_group_async` and `finalize_async` calls in `prove_async`). This forces CPU-mirror updates after every GPU dispatch, eliminating the GPU-authoritative-path races at the cost of dramatic slowdown.

Re-run xgboost with this change (evidence at `.recursive/run/wasm-webgpu-prover-perf/evidence/logs/sp-cr-xgboost-nogpuauth-*.txt`):
- `lift_async segment_index=0 elapsed_ms=168303` (167 s; vs 2.7 s with authoritative=true → **62× slower per lift**)
- `lift_async segment_index=1 elapsed_ms=167345`
- `lift_async segment_index=2 elapsed_ms=167185`
- Run timed out after 900 s; only 3 of 11 segments completed before timeout.
- **NO panic. NO verify_lift failure across the 3 completed segments.**

This strongly supports the race-condition hypothesis:
- With `gpu_authoritative_scope(false)` (CPU mirrors enforced), 3 lift-after-lift sequences complete cleanly. Earlier runs failed by segment 5 or 8 with `gpu_authoritative_scope(true)`.
- The R1 smoke fixtures (all single-segment) pass under either mode — single-segment doesn't exercise the lift-after-join race.

Conclusion: The bug is in the **multi-segment lift/join's GPU-authoritative async path** — specifically a missing async sync somewhere between a join's GPU outputs and the next lift's reads. The CPU-mirror path is correct; the GPU-authoritative path has a race that manifests non-deterministically at multi-segment boundaries.

The diagnostic change has been REVERTED in the worktree (back to `gpu_authoritative_scope(true)`) to keep the performance characteristics consistent with the rest of the R1 smoke matrix. The reversion lives at the same commit as this update.
