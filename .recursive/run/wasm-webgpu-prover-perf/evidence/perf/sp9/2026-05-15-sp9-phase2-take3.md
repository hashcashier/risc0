## Question

Take 2's failure-mode analysis pointed to a fix: collapse all
`min_binding_size` values to 0 across the 6 variable-byte_len
`create_bind_group_layout` call sites. With layout shape stable
across calls, phase 1's shape-keyed layout cache returns the same
instance every time, and a simple `(wgsl_ptr, entry_ptr)`-keyed
pipeline cache becomes safe.

Does it actually save wall time?

## Method

1. Edit `risc0/zkp/src/hal/webgpu.rs`:
   - 6 call sites changed: zeroize_elem, eltwise_add_elem,
     eltwise_sum_extelem, eltwise_copy_elem_slice, scatter,
     prefix_products_extelem. All `WebGpuBindingLayout::*(b, byte_len)`
     → `WebGpuBindingLayout::*(b, 0)`. The downstream
     `create_bind_group` calls still pass the actual byte_len so
     runtime validation is unchanged.
   - Add `compute_pipeline_cache: RefCell<BTreeMap<(usize, usize),
     WebGpuKernel>>` field to WebGpuHal.
   - `create_compute_kernel` checks cache first, compiles + inserts
     on miss.
2. Build wasm32 release (9m43s full rebuild + 4m23s test relink).
3. Run `hello_world_succinct_receipt_verifies` smoke.
4. Run `xgboost_succinct_receipt_verifies` x2 for wall measurement.

## Smoke result

`hello_world_succinct_receipt_verifies ... ok` in 3.32s. No
GPUValidationError this time — phase 2 take 2's layout-mismatch failure
is fixed.

The min_binding_size=0 collapse is the load-bearing change. The pipeline
cache rides on top of it.

## Why the pipeline cache doesn't help

Hypothesis: Chrome's WebGPU implementation already de-duplicates
compiled pipelines internally. The browser's GPU process likely caches
`createComputePipeline` results keyed by shader source SHA, layout
descriptor, and entry-point. Our cache adds:
- A `BTreeMap` lookup (O(log n) for n=30-40 unique keys).
- Two `RefCell::borrow*` calls per dispatch.
- A `WebGpuKernel::clone` (cheap, but real).

Without our cache, `create_compute_pipeline` hits the browser-side
cache after the first compile of each unique shader. The Tint compile
cost we hoped to amortize is already amortized by Chrome.

Net: we added Rust-side overhead without removing JS-side work.

Reason this wasn't anticipated: the SP10 retro projected SP9 corrected
at ~3-5% wall benefit, based on the assumption that pipeline compilation
was per-call. The compiler trace (which would show `createComputePipeline`
timings) was never collected directly.

## Reverted

Reverted the pipeline cache (field, init, lookup). KEPT the
min_binding_size=0 collapse on the 6 layout sites:

1. It is correctness-neutral (runtime binding-size validation
   already covers what `min_binding_size` checks statically).
2. It increases phase 1 layout cache hit rate across calls with
   variable byte_len -- already-landed phase 1 benefits.
3. It is a prerequisite for any future cache layered on the layout
   instance (e.g., SP6e bind-group cache by `(layout_instance,
   buffer_set)`).

Net diff: 20 insertions, 12 deletions in `webgpu.rs`. No pipeline
cache shipped.

## Implication for SP roadmap

SP9 as planned is effectively done -- phase 1 (layout cache, landed
e129c9728) + this partial take 3. The remaining 3-5% projection from
SP10 was unrealistic; pipeline caching is not a real lever on this
stack.

Remaining levers (priority order):
1. **iter-6d**: GPU witgen for exec_Top chunks via wgsl_pruner +
   `WebGpuCircuitHal::generate_witness`. Multi-day. Highest expected
   impact (~5-10% per SP10).
2. **SP6e**: bind-group cache for the 62 `create_bind_group` sites
   varying buffer instances. Unlikely to beat the pipeline-cache result
   above unless we can also avoid the `create_bind_group` JS call
   itself, not just deduplicate it. Worth a probe but lower expected
   value.
3. **iter-6d-deeper**: Chunk TopAccum/TopExtract more aggressively
   so their closures fit under the Chrome cliff after chunk0 rewrite.
