## What SP7 targets

The rv32im prove path spends ~4–5 s of its ~7–10 s per-segment wall in
two **CPU** phases (measured in iter-8/9 stage logs):
- `rv32im_witgen` — fills the execution-trace `data` buffer, ~1–2.2 s.
- `rv32im_accumulate` — fills the `accum` buffer, ~3.1 s.

Both are pure CPU on the WebGPU backend. `WebGpuCircuitHal`:
- `generate_witness` → `rust_steps::generate_witness` → per-cycle
  `step_Top(ctx, data, global)`.
- `step_accum` → `rust_steps::step_accum` → per-cycle
  `step_TopAccum(ctx, accum, data, global, mix)` + two prefix-sum
  passes.

SP7 = move these to the GPU so the per-segment CPU time collapses.

## The surface

- `step_Top` / `step_TopAccum` and all sub-steps live in
  `risc0/circuit/rv32im/src/zirgen/steps.rs.inc` — **30,468 lines of
  auto-generated zirgen circuit code**. This is not hand-written; it
  is emitted from the circuit DSL.
- The CUDA backend (`prove/hal/cuda.rs`) does *not* run `rust_steps` —
  it FFIs into `risc0_circuit_rv32im_cuda_witgen` /
  `..._cuda_accum`, which are CUDA kernels **also generated by
  zirgen** from the same DSL.
- The WebGPU backend has no zirgen→WGSL path. It falls back to the
  CPU `rust_steps`.

## The precedent — and the warning

SP3 already explored "generate WGSL kernels from the circuit" for the
*eval_check* polynomial. Result (memory `project_sp3_staged_kernel_ceiling.md`):
the staged/codegen WGSL was **~30× slower than the WGSL interpreter**
for rv32im — generated WGSL hits a Chrome/Dawn compile + execution
ceiling. The interpreter approach (`EVAL_CHECK_BASE_INTERPRETER_WGSL`,
~270 lines of WGSL that reads circuit "bytecode") is what shipped.

So SP7 faces the same fork as SP3 did — and SP3's evidence says
codegen is the dead end, interpreter is the viable path. But witgen
is structurally different from eval_check:
- eval_check is a pure polynomial evaluation, parallel across rows.
- witgen is per-cycle trace *filling*: it reads the preflight trace,
  does table lookups, and writes `data` columns. Cycles are largely
  parallel (the executor already ran; witgen just materialises the
  trace) but each cycle's step touches many columns with data-
  dependent control flow.
- accum has a genuine sequential dependency (the two prefix-sum
  passes at the tail of `run_accum_steps`).

## The forks

1. **WGSL interpreter for witgen/accum.** Emit the circuit's step
   logic as a compact "bytecode" the WGSL kernel interprets per cycle.
   Mirrors the shipped eval_check interpreter. Pro: one kernel, no
   30K-line codegen, dodges the Chrome compile ceiling. Con: witgen's
   step logic is far larger than eval_check's; the bytecode + the
   interpreter loop may be big, and interpretation overhead per cycle
   could erode the win.

2. **Codegen WGSL step kernels.** Add a zirgen→WGSL backend (parallel
   to its CUDA backend). Pro: native-speed kernels if Chrome compiles
   them. Con: SP3 measured exactly this approach at ~30× slower for
   rv32im — strong prior that it fails the same way.

3. **Partial / hottest-sub-step port.** Profile which sub-steps of
   `step_Top` / `step_TopAccum` dominate the 4–5 s, port only those to
   WGSL (interpreter or hand-written), leave the rest on CPU. Pro:
   incremental, lower risk, get *some* win fast. Con: the CPU↔GPU
   buffer shuttling between ported and un-ported sub-steps may eat the
   savings; needs measurement to know if it's net-positive.

## Estimated effort

The roadmap estimate is "3 weeks per circuit" for a full port. That
assumed codegen. An interpreter port is bounded differently — the
eval_check interpreter took the SP3 arc (many iters). A partial port
is the cheapest to *start* and the fastest to a measurable signal.

## Why SP7 is the right next lever (recap from iter 9)

- It cuts the per-segment CPU time directly (~4–5 s of ~7–10 s).
- It shrinks the per-segment CPU buffer peak — the ~1.8 GiB that
  forbids a segment prove from sharing wasm32's address space. If SP7
  brings the footprint down, the iter-9 dependency scheduler's ~8%
  heterogeneous-overlap win *extends to the segment phase*, which is a
  much larger fraction of total wall on segment-heavy fixtures.

So SP7 is both a direct wall lever and the unlock for the bigger
concurrency win.
